## 二、关键发现：真正的技术支点

### 2.1 Operit 的工具生态 = 31 个 JS 包，不是 Kotlin

`app/src/main/assets/packages/` 下的 31 个 `.js` 文件，**就是你（AI）当前正在使用的工具列表**：

```

minimax_draw.js  nanobanana_draw.js  openai_draw.js  qwen_draw.js
siliconflow_draw.js  xai_draw.js  zhipu_draw.js  automatic_ui_subagent.js
```

### 2.2 JS 包与宿主之间是**方法名字符串**级别的弱耦合

`quickjs/src/main/java/.../QuickJsNativeCompatScriptBuilder.kt` 注入的兼容层：

```js
root.NativeInterface = new Proxy({}, {
    get: function(_, property) {
        return function() { return callHost(String(property), JSON.stringify(args)); };
    }
});
```

即 JS 里写 `Tools.System.terminal.exec(id, cmd, timeout)` 时，宿主只收到：

```
__call("Tools.System.terminal.exec", "[id, cmd, timeout]")
```

**结论：移植 JS 包不需要改 JS 一行代码，只需要在 Kelivo 端实现一张按方法名分发的 dispatch 表。** 这是整个合并工作中最大的杠杆点。

### 2.3 Kelivo 上游**已经自带** proot 容器（重要）

这不是你加的，是上游 master 就有的（已用 GitHub API 验证）：


## 三、你的方案里需要修正的 4 处

### ❌ 修正 1：「移植 Operit MCP 终端工具 super_admin:terminal」

`super_admin` 不是 Kotlin 模块，是 **JS 包**（`assets/packages/super_admin.js`，388 行）。
它的「沙箱限制 / 输出回传」逻辑（如 `persistTerminalOutputIfTooLong`）都在 JS 里，**可直接复用**。
真正要写的只有宿主 API：`Tools.System.terminal.create/exec/screen/input`。

### ❌ 修正 2：「移植 Operit ADB 手机自动化能力」

**Operit 没有基于 ADB 的自动化。** 实测：
- Kotlin 里没有 adb 模块，`tools/adb/` 只是开发期脚本；
- 设备自动化的真实实现是 **无障碍服务**（`core/tools/defaultTool/accessbility/AccessibilityUITools.kt`）
  + **Shower 虚拟显示**（独立库 `showerclient/`）+ root/shizuku 工具。

要复刻必须移植 **AccessibilityService + Shower**，而不是「提取 ADB 指令代码」。

### ❌ 修正 3：「底层能力层完全从 Operit 源码提取」

Operit 的原生代码重度耦合自身 DI(Hilt)、ObjectBox、Compose UI，**不具模块独立性**。
真正能整块提取的只有两个：
- `quickjs/`（QuickJS JNI 模块，4 个 kt + 1 个 cpp）
- `terminal/`（`OperitTerminalCore` 独立仓库，需单独拉取，tarball 里是空的）

### ❌ 修正 4：「和 OperitAI 一模一样功能」

Operit 独有且 Flutter 侧**无法等价实现**的能力：
本地 GGUF/MNN 推理、Live2D/MMD/FBX 虚拟形象、悬浮窗对话、浏览器 Agent(Playwright 级)、
Shower 虚拟显示、无障碍全屏 UI 树读取、ToolPkg WASM 插件市场。

要在 Kelivo 达到「一模一样」= 把 Operit 整个原生层搬过去 = 等于重写 Operit，不是合并。

## 四、三个硬约束（决定「打包 APK」这一步做不做得了）

| # | 约束 | 后果 |
|---|---|---|
| 1 | 本容器**无 Flutter SDK / Android SDK / NDK / cmake** | 无法在本机编译任何 APK |
| 2 | Android 官方**不提供 aarch64 Linux 的 build-tools/aapt2** | 即使装上 Flutter，本机也编不出 Android 包 |
| 3 | Operit 构建需**私有归档** `subpack.zip`/`jniLibs.zip`/`libs.zip` | Operit 完整构建无法复现 |

**结论：阶段 5「编译、签名、打 APK」在当前设备上不可能完成，需要一台 x86_64 电脑（或 GitHub Actions）。**

## 五、可行的合并路径（修正版）

```
Kelivo (Flutter UI 主体，保留)
├─ 已有：proot Ubuntu 容器 / workspace / 终端 / MCP / 会话 / 模型 / 记忆 / workflow
├─ 缺：QuickJS 引擎  ← 从 Operit 移植 quickjs/ 模块
└─ 缺：Host API dispatch  ← 新写，把 Tools.* 映射到已有能力

Operit (能力来源)
├─ 31 个 JS 工具包        → 零改动直接复用（放进 assets）
└─ quickjs/ JNI 模块       → 整块移植到 kelivo/android
```

**移植的核心工作量 = Host API dispatch 表的实现**，见 `02-Host-API映射表.md`。
